# 从队友两条真实 Flash 路径检验候选顺序在有限搜索预算中的作用

已读 A28 的公开总结，知道 SMS 两组试完同六项且预测相同。此处预先限定一个 B 侧资源问题。只读原提交归档的两条六步探索历史，核验来源提交、同一目录和实际主分区、指标、最后封存模型、真实请求配额及执行顺序。按每个已发生的探索前缀，报告当时见过的最高训练内 macro-F1、相距该次六项中最高分多少、哪一步第一次见到最高分。分列共同第一项、实际 Flash 选择和预算用完后的本地选择。若某个候选的实测分数跨臂不一致，两条独立计算并报告。

给定第一项已经固定，另五项有 120 种顺序。用每条轨迹六个已经实际训练的分数枚举同一候选目录其它顺序的“截至第 k 次已见最佳分”均值与范围。这是基于已测分数的顺序计算，不相当于让同一个 Agent 真正在更短预算重新跑，也不预测未测候选。仅分析训练内，不读取新的外层标签，不归因于检查反馈、提示或接口模型。若归档没有某一状态的输入/逐行指纹，就标明能核查的边界。零训练、零模型请求。队友正在运行的 A29 独立记账。
