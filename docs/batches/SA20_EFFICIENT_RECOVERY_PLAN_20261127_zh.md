# SA20：相同调用预算下，让恢复更省、更有用

基线85550b5。A维护任务接入、恢复状态、提示与输出；本批不改B方法目录和排序。先落盘计划/脚本再运行，不覆盖SA19。

## 改动与假设

1. 允许LLM用一次inspect_batch请求两个结构工具。仍最多两次底层探查、最多3次Flash/路径，不自动扫包，不提供行值/像素。训练和预测两包的字段或NPZ键可同轮查完，留至少一次调用给B。
2. 按未决字段和已有结构事实识别语义空转，给LLM提示“查新证据、修正解释、或明确报告未决”。增加带字段/来源的report_unresolved动作，记录模型判断而不假装程序证明材料缺失。两个可恢复案例是防止过早放弃的阳性对照。
3. 已正常完成、用量已结算的JSON解析错误可进入同一恢复循环。网络/传输/结算/输出截断不重试；只给模型新的诊断请求，不补发原HTTP请求。此点先用模拟、可核对的结算响应验证，不伪装自然真实出错样本。

## 验收矩阵与资源

复用SA19已冻结的R1（字段改名）、R2（未知NPZ键）、R4（真正未定目标）原始包和oracle，逐字节核对。LLM自然选择工具和适配，不注入输出，不手选模型；从正式solve到新进程预测。R4无需训练，不能混入可恢复成功率。前后来自同一开发案例，属于顺序开发对照，不能归因于单个结构或当独立泛化结果。

每路径最多4次实际fit含refit、3次Flash、360秒、课程估计停止阈值¥0.30；三条最坏合计12fit/9API/¥0.90。仍用canonical真实账本、同16条已授权未知；原行/费用null不改。新增unknown/pending立即停当批，不自动重试。预期2–5分钟，不保证机器/接口时延。

先scripts/run_sa20_recovery_checks.py进行0fit/0API回归，之后scripts/run_sa20_recovery_live.py prepare冻结源码和原包，再run真实路径，最后独立审计。新目录写protocol/results/completion；密钥、包、模型、SQLite不进Git。

## 主指标与边界

- R1/R2完整恢复交付率、错误完成率、过早未决率；目标/指标/特征/输出九项oracle与新进程逐字节一致。
- 接入Flash数、工具底层数、B实际调用数、总token/课程折算/时间/fit，比较SA19原记录。
- R4完成有来源的未决报告，所用调用数及无新证据重复次数；不把少调用但猜目标当收益。
- JSON恢复的已计量响应与传输失败区分、共享次数/预算检查；模拟与自然真实证据分开。

本批不处理最终预测阶段任意异常，不改变安装读取器边界，不声称任意任务成功或预测分数提升。失败保留，在分析之后另立下一批，不反复重跑直到成功。
