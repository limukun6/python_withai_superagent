# 审阅前检查

v0.33真实三组试跑中，两个提案的实际选择是C从0.3降至0.1（加强正则化），理由支持这个方向，解释字段却又提出减弱正则化可能更好。自检和Reviewer均keep且没有明确处理相反理由。参数执行没有错误，暴露的问题是解释一致性和审阅质量。

v0.34在第二次调用前，使用已校验的原提案和同一DecisionState计算`proposed_diagnostics`。它包含当前候选相对已声明参照的参数变化、原有的有限文字审计提醒，以及新增的正则化方向提醒。它没有新的观测结果；`latest_configuration_comparison`仍描述历史实验，不能替代当前提案的比较。

三个架构的首次Planner提示保持相同。单Planner记录同样的检查而不增加调用；自检和Reviewer收到相同检查规则，只有角色提示不同。原提案、审阅前检查、最终提案及最终检查均写入`architecture_decisions.json`，原提案和提醒在第二次请求前写入事件。

方向规则只用于同一声明路线、唯一变化参数为C的情况。它扫描reason、hypothesis和assessment.interpretation中的有限英文“stronger/weaker”等正则化用语；明确比较替代假设、否定及历史描述的词语会让该句退出这个狭窄检查。跨路线、多参数变化、缺少参照、其它参数或未覆盖语言都不会被自动认定为方向一致。

这是启发式提醒，有漏报和误报可能。没有提醒不代表文字已验证，有提醒也不证明候选错误。不能根据提醒自动换候选、发起重试或追加费用，也不强迫Reviewer改变候选。Reviewer可以解释为何保留原方案，或者返回同一候选的完整提案来纠正文字；是否真的解释充分仍须审查原文。

summary记录原提案和最终提案的提醒数量，用于追溯变化，不把它们当作智能质量分数、准确率收益或因果证据。当前未加入“有提醒必须改选”的门槛，失败/费用上限/未知用量处理沿用原有规则。

正式比较需要冻结相同代码和训练机会，报告所有成本与失败。本次同时改进审阅信息并延长下一轮搜索次数，因此先前v0.33只能提供历史背景，不能把后续变化全部归因于增加预算或新增提醒。
